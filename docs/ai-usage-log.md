## 2026-10-22 OCR 試跑（p9）

- **我的 Prompt**：選擇方案 A：「下載 `qwen3-vl:4b-instruct`，pdf2md 原封不動照用」（另外兩個方案是沿用 `qwen3.5:9b` 但要改 pdf2md，或是讓 Claude 直接看圖轉錄）
- **Claude 做了什麼**：
  - `ollama pull qwen3-vl:4b-instruct`，用我的 pdf2md 跑 p9 英文欄
  - 第一次失敗（HTTP 400），直接呼叫 Ollama API 量測後找到原因，見下表
  - 在 `render_pages.py` 加上「裁掉四周空白和頁碼」，讓每頁的圖都放得進 `--ctx 8192`
  - 逐句對照原圖檢查 OCR 結果
- **實測數據**（Ollama 0.40.6、RTX 3070 Laptop）：

  | 送進模型的圖 | 尺寸 | prompt token | 結果 |
  |---|---|---|---|
  | 300 dpi 英文欄 | 1241×3508 | 4043 | `num_ctx` 4096 放不下 → HTTP 400 |
  | 300 dpi 英文欄＋`--ctx 8192` | 1241×3508 | 4043 | 成功，約 18 秒 |
  | 200 dpi 英文欄 | 841×2339 | 1913 | 成功，約 15 秒；文字和 300 dpi 逐字相同 |
  | 150 dpi 英文欄 | 631×1754 | 1115 | （只量 token，沒有跑 OCR） |
  | 300 dpi 去空白＋`--ctx 8192`（**採用**） | 1071×2376 | 約 2400 | 成功，約 16 秒 |

  - 這版 Ollama 的圖片 token 數和像素數成正比，大約每 1024 像素 1 個 token。pdf2md 的 HANDOFF 寫「Ollama 會把圖縮到固定大小，約 2347 token」，那是 0.22.1 版量到的，新版行為不同
  - `qwen3.5:9b` 預設開 thinking，pdf2md 的 request 沒有帶 `think: false`，所以沒有採用
- **OCR 品質**：p9 逐句對照原圖，**沒有發現錯字**；斷字（`mount-ing`、`tweez-ers`、`recom-mended`）都正確接回去。只有標題層級（`#`／`##`）不一致，整理母本時統一
- **最終 OCR 指令**：
  ```bash
  .venv/Scripts/python tools/render_pages.py
  .venv/Scripts/python <pdf2md>/convert.py ocr/pages/pNN_en.png --engine ollama --mode markdown --ctx 8192 -o ocr/raw
  ```
- **關鍵程式碼白話解釋**：
  - 視覺模型把圖切成小方塊（patch）來讀，圖越大方塊越多，佔的 token 越多。`num_ctx` 是模型一次能看的 token 上限，圖片加上文字指令超過上限，Ollama 就直接拒絕（HTTP 400）
  - `trim_to_content()`：找出有字的範圍（不含頁尾頁碼），四周留 10 pt 邊界後再裁切，少送一大片空白給模型

## 2026-10-22 批次 OCR、初校、整理母本

- **我的 Prompt**：回答 Claude 的兩個問題：「可以，跑剩下 5 頁」；原文錯誤的處理方式選「照原文＋校對註」

  - 初校：逐句對照原圖。p3、p5 段落長，把圖切成上下兩半放大後逐字比對
  - 整理母本 `ocr/td235_manual_en.md`：統一用 `##` 標章節、每頁標 `<!-- page: N -->`、Technical Data 改成一行一個 `key: value`
  - 用程式逐字比對「OCR 原始輸出」和「母本」，確認整理時沒有打錯字
- **初校結果**：
  - p3、p5、p9、p11：OCR 和原圖逐字相同
  - p7：OCR 把對照表讀錯了。原文每列是「1 = 10 mN 1」，OCR 多生出一欄，把最後一個數字重複兩次。已改回原文排法
  - p13：OCR 把原文的拼錯字「Rumble weightes」自動改成「weights」，已改回原文；其他數值都正確
  - 原文本身的錯誤（p7「1.5 mN」、p13「µm」等），OCR 都照原文保留，沒有擅自更正
- **AI 寫的內容（要由我確認或修改）**：母本裡 5 則「[校對註]」的文字是 Claude 擬的，內容只引用說明書其他頁、其他語言版本看得到的事實
- **關鍵程式碼白話解釋**：
  - 逐字比對用 Python 內建的 `difflib.SequenceMatcher`：把兩份文字切成單字序列，找出最長的相同片段，剩下的就是「新增／刪除／替換」。只要列出的差異都是刻意改的，就代表整理時沒有不小心改到原文
  - 為什麼「照原文＋校對註」：知識庫要能追溯到原文，所以不改原文；但如果只照原文，bot 可能篤定地回答錯的數字（例如 1.5 mN）。加上明確標示的校對註，bot 讀得到「原文前後不一致」，回答時可以提醒使用者
